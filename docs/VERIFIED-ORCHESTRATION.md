# Проверяемая приёмка оркестрации

Завершение хода backend, получение RESULT, завершение этапа и принятие проекта
являются разными событиями. `PlanningExecutionService` принимает проект только
через `AcceptanceGate`; количество DONE-этапов само по себе недостаточно.

## Критерии и доказательства

`Milestone.acceptanceCriteria` входит в спецификацию утверждаемого этапа.
Каждый критерий имеет постоянный локальный ID, описание, обязательность,
среду (`REVIEW`, `LOCAL_TEST`, `HERMETIC`, `REAL_BACKEND`, `MANUAL`) и ID проверки
приложения. При проверке ID дополняется ID этапа. Начатый этап нельзя переписать
предложением модели. Обязательность и среда видны при подтверждении плана.

Обычные изменения кода и вёрстки по умолчанию используют `REVIEW`: исполнитель
сам запускает соразмерные задаче проверки и передаёт ссылки на код, команды и
результаты. Проверяющий оценивает эти сведения. Упоминание теста или снимка экрана
не требует отдельной среды приёмки. Ручная приёмка пользователем не добавляется
автоматически только из-за изменения интерфейса.

Планировщик получает тот же реестр `AcceptanceChecks`, что и исполнитель плана.
Новые обязательные критерии в отдельной среде без зарегистрированного `checkId`
с совпадающей средой возвращаются модели на исправление до предложения плана.
Если недоступную среду явно требует пользователь, планировщик объясняет
ограничение и уточняет его до составления плана. Критерии сохранённых планов
автоматически не ослабляются.

Для старых планов без массива критериев сохраняется один критерий `REVIEW`
из acceptance/description. Это оценка отчёта, не доказательство запуска тестов
или реального сервиса. Полностью принятый такой план не получает автоматически
свидетельства о production-проверках. Исторический COMPLETE без записи приёмки
при возобновлении проходит новую итоговую проверку.

Модель проверяет каждый критерий отдельно и возвращает `AcceptanceFinding`:
точный ID, PASS/FAIL/NOT_RUN/SKIPPED/BLOCKED, ожидаемое, наблюдаемое и ссылки на
артефакты. Её общий флаг `passed` не участвует в итоговом решении. Отсутствующие,
повторяющиеся и неизвестные ID отвергаются с ограничением в три исправления.

Для любой среды кроме REVIEW дополнительно нужна квитанция `AcceptanceChecks`.
Реестр создаётся кодом приложения и внедряется в `PlanningExecutionService`.
`RegisteredAcceptanceCheck` фиксирует среду и проверяющую функцию; исполнитель
не может зарегистрировать её своим JSON, подставить команду оболочки или записать
квитанцию. Функция возвращает статус, наблюдение и ссылки на сохранённые
доказательства. ID критерия и снимок добавляет приложение.

По умолчанию реестр пуст: незарегистрированная проверка остаётся NOT_RUN.
В этом изменении не добавлены живые GitHub/Pi/Codex проверки, OS-изоляция или
API очистки памяти backend. Их реализация требует отдельных проверяющих функций
и соответствующего окружения. Пустой реестр не подменяет их LLM-оценкой.

`AcceptanceGate` проверяет точное совпадение критериев, снимка и среды квитанции.
Квитанция PASS без ссылки на артефакт недостаточна. Обязательные FAIL, BLOCKED,
NOT_RUN и SKIPPED препятствуют принятию; необязательные результаты сохраняют
свой исходный статус. Пропущенный этап не получает PASS итоговой проверки.

Проверяющий классифицирует каждый отказ: `WORKER` — исправимое несоответствие,
`EVIDENCE` — недостающие доказательства, `UNAVAILABLE` — недоступная проверка,
`OWNER` — решение владельца, включая уже совершённое нарушение HEAD/index.
Без классификации автоматическая доработка не запускается. Повтор той же причины
(`criterionId`, статус и стабильный `problemKey`, для старых записей — наблюдение)
останавливает автоматический цикл; изменение формулировки при том же ключе его
не возобновляет. Отдельный ресурсный лимит повторов пользователя также сохраняется.
Историческое нарушение требует обсуждения с оркестратором; интерфейс не предлагает
повторить исполнителя. Это не обход FAIL и не разрешение изменить критерии.
Отсутствие квитанции приложения не запускает повторное редактирование файлов.

При недоступной, неполной или устаревшей проверке доступны «Проверить автоматически»,
«Продолжить без проверки» и «Оставить остановленной». Второй вариант обрабатывает
приложение по явному ответу пользователя без интерпретации моделью. Решение
`AcceptanceWaiver` сохраняет запуск, точный критерий, попытку, снимок и время.
Решение охватывает все критерии выбранного этапа, включая ранее принятые:
«без проверки» не запускает оставшуюся часть проверки заново.
Пропущенные проверки получают `SKIPPED`; приёмка — `ACCEPTED_WITH_SKIPS`.
Это разрешает продолжение и перенос результата, но не утверждает успешную проверку.
Сводка и история показывают пропуск. Общая кнопка пропуска вопроса такого решения
не принимает.

Итоговая проверка учитывает эти решения в том же запуске и проверяет остальные
критерии. Новые критерии и новый запуск требуют нового решения. Ошибку выполнения,
известный FAIL или неизвестный результат внешней команды
этот выбор не обходит. Существующие остановленные планы получают варианты из
сохранённой записи приёмки без изменения их требований.

Если все проверки записи явно пропущены, снимок файлов не подтверждается и не
сравнивается повторно: запись означает только продолжение по решению пользователя.
Изменение файлов не превращает такой пропуск в новую блокировку. При частичном
пропуске устаревание оставшихся результатов сохраняет отметки `SKIPPED`.

При восстановлении учитывается решение старой версии «Продолжить без проверки»,
которая сохраняла пропуск только неподтверждённых пунктов. Если тот же этап снова
заблокировался на проверке, сохранённые критерии совпадают и запуск остаётся RUN,
пропуск расширяется на весь этап и выполнение продолжается без нового ответа.
Остановка, пауза, другой запуск и новые требования автоматически не отменяются.

## Снимок и восстановление

Desktop вычисляет SHA-256 содержимого tracked и неигнорируемых untracked-файлов,
индекса, имён, executable-флага и целей символических ссылок. Чтение не меняет
индекс и не запускает Git-фильтры или fsmonitor. Неподдерживаемые файлы и
недоступный снимок не дают положительной приёмки. В папке без Git учитываются
все файлы; генерируемые файлы также могут инвалидировать такую проверку.

Отчёт исполнителя связывается со снимком при передаче управления. Итоговая
проверка имеет снимки до запуска, после оценки и на границах переноса результата.
Для выполняемых проверок изменившееся дерево или критерии дают STALE и останавливают принятие. Это
консервативная проверка всего дерева: изменение независимого файла тоже может
потребовать новой проверки. Снимок не блокирует внешние редакторы и не является
OS-изоляцией. Факты о внешней среде подтверждает соответствующий host-check.

`StageAttempt.acceptanceRecord` и запись приёмки переноса сохраняют точные
замечания и доказательства. Они передаются следующему планированию, включая
переход к предложению доработки, а прежние попытки остаются в истории.
Пауза во время проверки запрещает перенос и переход в DONE.

## Команды, ожидания и отображение

Планировщик проверяет runId при применении команды и возвращает типизированные
конфликты STALE_RUN/ALREADY_DELIVERED. Квитанции обеспечивают повторяемость уже
принятых команд. Отправленные правила неизменяемы. Повтор интерпретации получает
текущее состояние плана, правил и приёмки. Автоматическая доставка не может
подтвердить предложение или отменить пользовательскую остановку.

Граф ожиданий включает зависимости этапов и подписки приостановленных
исполнителей. Ожидание собственного завершения, завершения зависимого этапа
или всего запуска отвергается до сохранения операции. Исторический цикл
выявляется при возобновлении исполнения. Существующие ограничения цепочек
самосообщений, повторных CONTINUE и повторов проверки сохраняются.

Видимые фрагменты ответа имеют отдельные пространства ID для интерпретации,
её повторов и планирования. Они сохраняются при переходах и записи результата.
Отклонённая интерпретация помечается как неприменённая, не исчезает с экрана
и не считается выполнением действия.

## Регрессии

`AcceptanceTest` проверяет подмену среды, отсутствие квитанций, изменение
критериев, неполную приёмку и восстановление. `VerificationSnapshotTest`
проверяет реальные staged/unstaged/untracked изменения и сохранность индекса.
`PlanningExecutionServiceTest` покрывает STALE, паузу, полный набор критериев,
отсутствие результата backend и остановку при недоступной живой проверке.
`MessageSchedulerTest` покрывает циклы и устаревший runId.
`PlanningChatServiceTest` проверяет сохранение фрагментов при повторе и REFINE.

Результат этих тестов относится к поведению приложения и фикстурам; он не
является приёмкой внешних backend-сервисов или пакетов SKILLS.

## Видимость передачи и проверки (10 сентября 2026)

Полный текст поручения сохраняется отдельно для каждого `StageChatTurn` и
показывается отправителю и исполнителю. Старая краткая квитанция расширяется
только при наличии сохранённого текста соответствующего хода. Утраченный текст
прошлых ходов не восстанавливается из предположений. В обычной доставке
`SessionContextPacket` обе стороны видят один текст и метаданные контекста.

`AcceptanceRecord` сохраняет идентификатор решения, модель проверяющего, время,
снимок и findings. Решение выводится обеим сторонам отдельно от RESULT исполнителя.
Проекция восстанавливается из сохранённой записи без повторного вызова модели.
Старые записи без модели явно показывают отсутствие этих сведений.

Новые оркестрационные планы используют изолированную рабочую копию. Ответ модели
не может переключить их на shared checkout. Desktop проверяет также сохранённые
пути: исполнение в той же пользовательской Git-рабочей копии (включая алиасы и
подкаталоги) блокируется до запуска. Старые планы, результаты и файлы остаются на
месте; автоматическая миграция незавершённого Git-состояния не выполняется.
