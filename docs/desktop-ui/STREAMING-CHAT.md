# Плавный потоковый вывод в чате

Документ для задач, где меняется отрисовка ответов агента, которые приходят
по частям: новые строки, растущий ответ, шаги инструментов, живой черновик
прогона. Общие требования к отзывчивости, кадрам и пути к цели —
[interaction-quality.md](../../skills/magicpaper-desktop-ui/references/interaction-quality.md);
здесь — только потоковая лента.

Жалоба, которую этот документ предотвращает: «пока агент печатает, интерфейс
прыгает и мигает». У любого видимого скачка одна из четырёх причин, и у каждой
уже есть владелец в `:designSystem`. Новый механизм рядом с ним не добавляется.

## Что такое «прыжок» на самом деле

1. **Переякоривание.** Обновление прокручивает ленту к *началу* растущего
   сообщения: каждая новая строка бросает взгляд читателя в первую строку, а
   свежий текст остаётся за нижним краем.
2. **Изменение высоты выше вьюпорта.** Уже разложенные строки меняют высоту:
   повторный разбор всей ленты, сброс состояния раскрытия, позднее измерение
   картинки или вложения, padding, зависящий от флага потоковой передачи.
3. **Работа на каждый чанк.** Одна запись состояния, один разбор Markdown и один
   relayout на каждый сетевой токен. Кадры теряются, текст «дёргается».
4. **Борьба с читателем.** Автоскролл продолжается, пока пользователь крутит
   вверх, либо логика слежения принимает собственную докрутку за жест и навсегда
   отпускает ленту.

## Карта владельцев: что это уже реализует

| Задача | Владелец | Поведение, которое нельзя ломать |
| --- | --- | --- |
| Держать конец ленты | `paperStickToBottom(listState, resetKey)` в [ChatScroll.kt](../../designSystem/src/commonMain/kotlin/io/aequicor/magicpaper/ui/components/ChatScroll.kt) | Слежение за *нижним краем* последнего элемента, а не за его началом. `pinToEnd` повторяет докрутку, пока `canScrollForward == false`: элемент ниже вьюпорта ещё не измерен. `resetKey` — id чата или сессии, поэтому открытие и переключение сразу показывают конец. |
| Определить, кто владеет прокруткой | `PaperChatScrollState`: `anchor`, `disclosureRevision`, `navigating`, `interruptNavigation` | Жест читателя, переключение раскрытия и явная навигация всегда выигрывают; слежение возвращается только на настоящем дне. Решения читают свежий снимок `layoutInfo`, а не conflated-значение из `snapshotFlow`. |
| Прижать хвост до отрисовки | `scroll.onLayoutCompleted` → `requestScrollToItem` | Коррекция из placement-колбэка именно *запрашивается*: принудительный layout там повторно вошёл бы в measure. |
| Показывать streamed-текст | `rememberPaperStreamingText` / `StreamingTextBuffer` в [StreamingText.kt](../../designSystem/src/commonMain/kotlin/io/aequicor/magicpaper/ui/components/StreamingText.kt) | Чанки коалесцируются до ~30 fps (`STREAM_FRAME_NANOS`); всплеск догоняет за ~160 ms ростом скорости (`CATCH_UP_MILLIS`, `MIN_CHARS_PER_MILLI`), а не очередью. Анимируется только новый суффикс; завершение и любая замена не-префикса применяются сразу. Суррогатные пары не разрываются. |
| Разбирать Markdown вне UI-потока | `rememberChatMarkdownDocument` + `ChatMarkdownDocuments` в [MarkdownDocument.kt](../../designSystem/src/commonMain/kotlin/io/aequicor/magicpaper/ui/components/MarkdownDocument.kt) | Разбор на `Dispatchers.Default`; новые чанки conflated, пока один разбор завершается, поэтому длинный ответ никогда не остаётся неотрисованным. Результат отбрасывается, если текущий текст больше не начинается с него. Ограниченный LRU-кеш (6 документов / 1M символов) переживает удаление ленивых элементов; streamed-текст не кешируется. |
| Ограничивать длинный ответ | `PaperChatMarkdown`, `MESSAGE_PREVIEW_CHARS`, `PaperMessagePreview` | Анимируется и отрисовывается inline только текст в пределах бюджета preview; остальное показывается превью и раскрывается, а не растёт бесконечно. |
| Дробить сообщение на ленивые элементы | `rememberPaperInlineMessageParts`, `PaperInlineMessageParts.contentType`, `CodingMessageFragment` | Раскрытое сообщение становится несколькими элементами ленты со структурным content type: абзац не переиспользует дерево таблицы или заголовка. |
| Асинхронное раскрытие не крадёт прокрутку | `PaperPreserveInlineExpansion` | Разбор, завершившийся после клика, поднимает `disclosureRevision` и оставляет читателя на месте. |
| Координаты строк и состояние жеста | `PaperChatScrollItem`, `LocalPaperChatScrolling` | Координаты живут в обычном держателе, а не в Compose state: их публикация инвалидировала бы всё сообщение при переиспользовании. Меню закрываются во время жеста; `PaperMessageActions` сохраняет один слот композиции (`Box`), чтобы markdown, картинки и раскрытия не пересоздавались дважды за одно движение колеса. |
| Сборка ленты | `CodingScreen` / `ChatScreen`: `items(fragments, key = …, contentType = …)` | Один ленивый элемент на шаг (прогон содержит тысячи шагов), устойчивые ключи, переживающие превращение черновика в сохранённый ответ (`CodingStep.toolIdentity`), content type по виду шага или роли. |
| Края ленты | `paperChatTopShadow`, `contentPadding` из измеренной высоты шапки и футера | Морозная полоса и отступы зависят от измеренной высоты оконных элементов и не должны зависеть от содержимого сообщений. |

## Правила для нового и изменяемого чата

1. **Используй существующее слежение.** Лента собирается через
   `paperStickToBottom(listState, sessionId)`, строки оборачиваются в
   `PaperChatScrollItem(scroll, key)`. Никогда не пиши
   `LaunchedEffect(text) { listState.scrollToItem(lastIndex) }`: это
   переякоривание к началу сообщения и борьба с читателем.
2. **Устойчивая идентичность строки.** Ключи берутся из идентичности сообщения и
   шага, а не из индекса, и переживают сохранение черновика, вставку шага и
   раскрытие сообщения. С индексными ключами каждая новая строка
   переиспользует чужой элемент — это и читается как мигание.
3. **Поток только у живого хвоста.** `streaming = true` передаётся только
   последнему ответу активного черновика или живому шагу инструмента (см.
   `live = …` в `CodingScreen`). Исторические строки получают итоговый текст
   сразу: открытие сессии не проигрывает появление текста заново.
4. **Не больше одной записи состояния на кадр.** Сетевые чанки не передаются в
   композицию напрямую. Для новой потоковой поверхности используется
   `rememberPaperStreamingText`, а не ещё один тикер; авторитетный текст живёт в
   сервисе, чтобы завершение не зависело от анимации.
5. **Рост только вниз.** Ничего выше вьюпорта не меняет высоту из-за потока: ни
   зависящих от флага отступов, ни производной типографики, ни нерезервированного
   места под изображения и вложения. Для асинхронных медиа резервируй минимальную
   высоту или запомненное соотношение сторон.
6. **Читатель всегда выигрывает.** Любой жест, переключение раскрытия и явная
   навигация отменяют слежение; возвращает его только
   `canScrollForward == false`. Никаких эвристик по размерам сообщений и
   смещениям «пользователь, наверное, прокрутил». Пока
   `isScrollInProgress`, автоскролл не выполняется, а при отсутствии слежения
   остаётся видимый способ вернуться в конец (`canScrollToEnd`).
7. **Ограниченная работа на чанк.** Никакого повторного разбора всей ленты,
   перестроения всего AST Markdown на токен, регуляров и форматирования на каждый
   символ. Ограниченные операции над префиксом текущего хвоста допустимы.
8. **Движение локальное и прерываемое.** Строка целиком не fade/slide/scale на
   каждое обновление; каретка или пульсация статуса не инвалидируют ленту — они
   ограничены маленьким composable и останавливаются в покое. При reduced motion
   появление текста вырождается в мгновенный текст: читатель получает все строки,
   но без анимации.
9. **Сохраняй позицию при раскрытии.** Сворачивание идёт через
   `preserveCollapsedItem`, раскрытие — через `paperChatDisclosure`, чтобы
   видимая первая строка оставалась на своём месте экрана, а не уезжала в offset 0.
10. **Держи границу.** Всё перечисленное живёт в публичном API `:designSystem`.
    Фича потребляет `Paper*`; если новой потоковой поверхности не хватает
    поведения, сначала узко расширяется `:designSystem` с документацией и тестом,
    а не локальный аналог в модуле фичи.

## Проверки

Существующие тесты, которые защищают это поведение — запускай те, что затрагивает
изменение:

- `designSystem`: `StreamingTextBufferTest`, `StreamingTextRenderTest`,
  `LongMessageRenderTest`.
- `feature/session/impl`: `CodingChatScrollTest`, `ChatScrollToBottomTest`,
  `ChatChatScrollToBottomTest`, `CodingChatRowsTest`, `ChatLongMessageRenderTest`,
  `LargeCodingChatRenderTest`, `RequestPinsRenderTest`,
  `ActiveCodingChatRenderTest`.

Ручная приёмка на реальной desktop-сборке, длинный прогон (сотни шагов) с высоким
темпом токенов:

- Прокрутил вверх во время потока — лента стоит на месте, слежение возвращается
  только после возврата к концу.
- Переключил раскрытие во время потока и свернул длинный ответ — без прыжка в
  начало, кликнутый заголовок остался на месте.
- Изменил размер окна, переключил сессию и вернулся, раскрыл сообщение во время
  потока — без переякоривания и без повторного появления уже показанного текста.
- Смотри тайминг кадров во время потока и во время быстрой прокрутки колесом по
  той же ленте; называй потерянные кадры и их причину. Превью и unit-тесты FPS не
  доказывают: фиксируй, что именно измерено, а остальное помечай `NOT_RUN`, как
  требует [interaction-quality.md](../../skills/magicpaper-desktop-ui/references/interaction-quality.md).
