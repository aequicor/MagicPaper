# Целевая архитектура студии

Замысел: детерминированное ядро с недетерминированными органами. Скелет — обычный код,
принимающий решения по явным правилам; модель отвечает только там, где нужна догадка,
и всегда значением из закрытого множества, а не свободной командой.

Документ описывает, куда движется исполнение сессий, и в каком порядке туда идти.
Текущие границы модулей — в [MODULES.md](MODULES.md), владельцы и проверки — в
[CODEMAP.md](agent-workflows/CODEMAP.md) и [VERIFICATION.md](agent-workflows/VERIFICATION.md).

## Что стоит

- **Три режима с правами, навязанными кодом.** `CodingInteractionMode.CODE/RESEARCH/PLANNING`;
  `changeInteractionMode` запрещает смену на ходу, `ToolDefinition.allowed` решает, какой
  инструмент доступен в каком режиме и по чьим полномочиям. Это правило, а не просьба к модели.
- **Зигота и исполнители.** `CodingSessionRole.ORCHESTRATOR/WORKER`, `SessionTreeRuntime`,
  `OrchestrationService`; у каждой дочерней сессии свой контекст.
- **Судья со свежим контекстом.** `MilestoneVerifier.verify(milestone, goal, report, profile)`
  получает пакет улик, а не историю диалога, и решает с нуля на каждом вызове.
- **Изоляция исполнения.** `GitPlanningWorkspace`, worktree попыток, манифест переноса,
  сверка процессов по PID и владельцу.
- **Разделение платформ.** `:feature:coding:impl` объявляет только jvm-цель; Android и браузер
  его не компилируют, хосты без агента связывают `UnavailableCodingFeature`. Защищено правилом
  `DESKTOP_ONLY` в [verify-module-architecture.py](verify-module-architecture.py): зависеть на
  него разрешено только из `jvmMain`/`jvmTest`. Авторитетная проверка — `compileMigrationTargets`.
- **Словарь инструментов отдельно от исполнения.** `:feature:tools:api` — каталог, схемы,
  матрица «режим → инструмент → полномочия», типы отказа. Ни рантайма, ни Koin.
- **Узкий порт чата.** `DefaultChatService` зависит от `ChatBackend` (четыре метода), а не от
  всего `CodingRuntime`.
- **Восемь решений вынесены из службы в чистые функции** — см. «Стейт-машина» ниже.
- **Журнал событий: хранилище и писатель** — см. «Журнал» ниже.

## Что осталось, по порядку

Порядок не произвольный: каждый следующий шаг опирается на предыдущий, и два шага меняют
инвариант хранения — их нельзя делать вместе ни с чем другим.

### 1. Исходы намерений

Сегодня пару «намерение → исход» имеют только `stop-intent → stop-confirmed` и
`apply-intent → apply-complete`. У остальных намерений (`prepare`, `stage-workspace`, `agent`,
`capture`, `merge`, `conflict-agent`, `delivery-conflict`, `final-verification`) исхода нет,
поэтому вопрос «какие намерения остались без исхода» пока отвечает «все».

Работа не механическая. Исход обязан писаться **на всех путях выхода**, включая ранние
`return` и отмену корутины, иначе прерванный эффект не отличить от провалившегося — а это
ровно то различие, ради которого журнал существует. Исход должен называть, чем кончилось:
выполнено, отказано, прервано. Отсутствие записи означает «неизвестно» и только это.

### 2. Читатель журнала

`fun unsettled(stream): List<JournalRecord>` — намерения без исхода. Здесь журнал начинает
окупаться: ответ соединяется с `StageResumption.UnknownOutcome`, `SessionQuarantineRecovery`
и `reconcileCodingQuarantine(sessionId, confirmed)`, у которых сегодня нет общего источника
правды. Выходов из неизвестного исхода по-прежнему ровно два: улика от `NativeReceiptRecovery`
и подтверждение человека. Никогда по таймауту, никогда повтором.

### 3. Остаток решений `executeStage` → `reduce`

В службе ещё решают: блок починки по сохранённой приёмке (`repairRetries` + `acceptanceRecord`),
возобновление координации, сборка промпта, допуск задания (`prepareAttempt` и сверка тождества),
блок проверки (приёмка → вердикт → повтор починки), блок объединения, завершение этапа.

Критерий готовности к `reduce`: в `executeStage` не осталось ветвлений, зависящих от состояния
попытки, — только исполнение эффектов и чтение чистых функций.

```
sealed interface StageEvent    // Prepared, Started, WorkerTurnEnded, PlannerDecided,
                               // VerificationPassed/Failed, MergeStarted/Succeeded/Failed,
                               // UserAnswered, EventFired, TransportFailed, Interrupted,
                               // RetryAuthorized, NativeEvidence, UserConfirmedOutcome
sealed interface StageEffect   // RunWorker, RunVerifier, RunMerge, AskUser, WaitForEvent,
                               // RecordJournal, Quarantine, Finish
fun reduce(state: StageState, event: StageEvent): StageTransition   // без Clock, Random, корутин
```

Место — `core/model/.../domain/planning/StageMachine.kt`. Отдельный модуль `:core:machine` не
заводить: `reduce` — около тридцати строк каркаса, а State/Event/Effect суть доменные типы.

Сериализуемая форма `StageAttempt` в этом шаге не меняется: два адаптера
(`toState`/`applyTo`) держат формат на диске байт-идентичным. Схлопывать флаги в один
дискриминатор — только после того, как редьюсер докажет их избыточность, и отдельной миграцией.

### 4. `OrchestrationService`

2747 строк, множество событий ещё не замкнуто. Браться только после того, как редьюсер этапа
докажет форму на замкнутом множестве писателей.

### 5. Реактивность

UI — проекция состояния. Компонент читает одно состояние и отправляет действия; исполнение,
черновики и фоновые задачи принадлежат службам, переживающим экран. Проекции — чистые функции,
которые тестируются подачей списка событий и сверкой снимка, без моков служб. Раньше редьюсера
делать нечего: проецировать пока нечего, кроме тех же флагов.

### 6. `Plan` как проекция журнала

Меняет CAS-контракт `PlanningStore` (`expectedRevision`, `checkpointMessageEvents`). Самый
рискованный шаг. Делать последним и не вместе с другой сменой инварианта.

### 7. Классификатор стратегий

Когда в журнале накопится статистика: детерминированный детектор считает метрики → модель
возвращает метку причины из закрытого перечня → выбор из заранее одобренной палитры → исход
обратно в журнал. Свободное действие модель не возвращает никогда.

Достаточно `core:ai:api LlmGateway`. Сторонний LLM-фреймворк имеет смысл только когда
понадобятся цепочки с вызовом функций на всех платформах — тогда же станет возможен общий
прямой путь для чата (см. KDoc `ChatBackend`). JVM-only библиотека сломает `commonMain`,
где живут js, wasmJs и android.

## Стейт-машина: что уже вынесено

Работа идёт срезами: решение за решением уходит из службы в чистую функцию `core:model`,
каждый раз под полным набором тестов. Так работу можно остановить в любой момент, не оставив
половину решений в машине, а половину в службе.

| Что | Где | Что было |
| --- | --- | --- |
| Операции журнала плана | `PlanJournalOperation` | свободная строка, читаемая сравнением |
| Чего ждёт попытка | `StageWaiting` | четыре независимых поля, сочетания на `if` |
| Как возобновить попытку | `StageResumption` | порядок проверок, державшийся на порядке строк |
| Что значит событие движка | `StageEngineSignal`, `StageAttempt.after`, `StageRunResult` | четыре копии одного `when`, разошедшиеся в мелочах |
| Повторять ли сбой | `RetryDecision`, `PlanningRetryPolicy.decide` | четыре написания одного решения; часы и случайность внутри службы |
| Описывает ли сохранённый план ход в руках | `CheckpointDrift` | цепочка `if` с четырьмя полями тождества и без имени |
| Где стоит разрешение конфликта | `MergeProgress` | `AttemptPhase?` с чужим смыслом; три вопроса к нему в двух циклах |
| Должен ли планировщик ответ | `CoordinationState` | `Boolean?`, где `null` читался тремя способами в пяти местах |

Общее у всех восьми: несущий порядок или несущее разногласие, которое держалось на порядке
строк и нигде не было названо. Форма на диске не менялась ни разу — это условие, при котором
срез не требует миграции.

## Журнал: что уже стоит

`EventJournal` в `:core:storage:api`, `DurableEventJournal` в `impl` (имя по соседям —
`DurableSecretStore`, `DurableDraftRepository`), член `events` в `PersistenceStores`.
`StorageArea.EVENTS` очищается тем же сбросом, что и состояние, — ради этого отдельный модуль
`:core:journal` и не нужен.

Гарантии, покрытые тестами: одна запись — один ключ, ничего не переписывается; seq монотонен
для всех потоков и всех экземпляров (включая вкладки браузера) и переживает перезапуск; номер
резервируется до записи, поэтому обрыв оставляет пропуск, а не затёртую запись; потерянный
курсор восстанавливается по самим записям; нечитаемая запись — ошибка, а не молчаливо
укороченная история; `drop(stream)` убирает поток целиком и не отматывает seq.

Писатель — `PlanningStore.journal(...)`, владелец записи планов. Запись дописывается **до**
сохранения плана: журнал самого плана лежит внутри документа, и потерянное сохранение уносит
запись с собой, а намерение, которого никто не записал, неотличимо от эффекта, которого никто
не запрашивал. Поток именуется планом, а не проектом. `deletePlan` и `wipe` убирают поток
целиком — единственная граница роста. Подробность записи — схема плана (`PlanJournalSubject`),
журналу она непрозрачна: словарь знает тот, кто пишет.

## Где план разошёлся с реальностью

Записано, чтобы расхождения не всплывали как сюрприз.

- **`:feature:coding:api` не заведён.** Контракты кодинга (`CodingFeature`,
  `CodingFeatureDependencies`, `UnavailableCoding*`) легли в `:feature:session:api`, потому что
  они и так ссылались на его типы, а отдельный api-модуль добавил бы только ещё одну границу.
  Платформенная изоляция от этого не пострадала: её даёт `:feature:coding:impl`.
- **Движок инструментов остался у кодинга.** План выносил `AgentTools.kt` в `:feature:tools:api`
  на том основании, что чат потеряет инструменты, уйдя с `CodingRuntime`. Основание оказалось
  ложным: чат жил в `session:impl` рядом с движком, а все тесты инструментов ходят через
  `ToolHost`. Переехал только словарь.
- **Чат остался на движковом пути.** Решение пользователя: поведение не менять, пока не появится
  KMP-фреймворк с цепочками вызовов. Вместо разрыва — узкий `ChatBackend`; две реализации не
  взаимозаменяемы, и выбор принадлежит платформе, которая собирает приложение.
- **Общий дом представления — `:feature:transcript`**, а не третий api-модуль кодинга.

## Долги

- `:feature:tools:api`, `:feature:transcript`, `:feature:session:api` — ноль собственных тестов.
- `ToolHost` — 16 изменяемых портов (было 13, стало больше). Его надо **удалить** в пользу
  конструкторной инъекции, а не переселить.
- `:app:jvmTest` — два отказа (`SessionAutoArchiveServiceTest`, `RequestPinViewModelTest`),
  воспроизводятся на `c629d130` и старше. Не «чинить» ослаблением проверок.
- `maxParallelForks` в тестах замерен и отвергнут: ускоряет coding и session, ломает `:app`
  (`SidebarRestorationTest` — 315 s вместо 0.68 s). Не возвращать без решения этой причины.

## Куда не идти

- Не разделять `:app`: это композиционный корень нужного размера.
- Не переносить `ToolHost` в модуль инструментов — его надо удалить, а не переселить:
  изменяемые порты и есть проблема.
- Не делать `OrchestrationService` первым срезом стейт-машины.
- Не менять сериализуемую форму `StageAttempt` в одном шаге с редьюсером.
- Не переводить `Plan` в проекцию журнала в одной программе со сменой границ модулей.
- Не строить механизм без потребителя: журнал получил писателя тем же вечером, что и хранилище,
  и читателя получит до того, как в нём появится что читать.
