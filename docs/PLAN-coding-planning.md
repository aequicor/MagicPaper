# План: плагин «Планирование» для кодинг-сессий

> Исторический проект первой версии. Актуальная реализация дерева решений,
> параллельного исполнения и восстановления описана в [PLANNING.md](PLANNING.md).
> Линейный `PlanRunner` ниже сохранён для совместимости; новый плагин использует
> сервис приложения `PlanningExecutionService`.

Цель: кодинг-задачи выполняются не «одним промптом», а по подготовленному плану:
1. каждая модель сопровождается **досье** — в какой области она хороша и насколько (заполняет
   человек или модель один раз ищет о себе в публичных источниках);
2. задача раскладывается в **визуальный график мэилстоунов**, за каждым закреплён оптимальный агент;
3. **автоматическое выполнение**: каждый шаг выполняется своим агентом и проверяется на
   достижимость — план останавливается на первом недостижимом шаге.

Ограничения проекта: KMP (jvm/web/android), без DI-фреймворков, без материальных иконок
(текстовые глифы), хранение — `KeyValueStore`, плагин — через `MagicPlugin` SPI.

## Архитектура (чистые слои, как в остальном коде)

### Домен (`domain/`)

| Файл | Содержимое |
|---|---|
| `Planning.kt` | `Milestone`, `MilestoneStatus` (PENDING/ACTIVE/DONE/FAILED/SKIPPED), `Plan`, `PlanStatus`, `ModelDossier` (+ `DossierSource` USER/WEB/HEURISTIC), порт `PlanningRepository`, `PlanDraft`/`MilestoneDraft`, `AgentMatcher` (подбор агента: косинус шага к сильным сторонам досье с префиксным стеммингом ×0.7 + оценка ×0.3) |
| `PlanComposer.kt` | Разбивка цели в цепочку шагов: модель → JSON-массив (2–6 проверяемых вех, с подсказкой-именем агента), без модели — честный одношаговый план с пометкой. Имена агентов сопоставляются с реальными профилями (точное имя → косинус > 0.2 → пусто) |
| `DossierResearcher.kt` | «Модель ищет информацию о себе»: запрос в поисковый движок по имени модели и провайдеру → контекст → модель сводит `{strengths, rating}` со ссылками. Фолбэки: без модели / сбой — эвристика по имени (источник HEURISTIC) |
| `MilestoneVerifier.kt` | Порт `MilestoneVerifier` + `LlmMilestoneVerifier`: модель-судья читает критерий шага и отчёт агента, вердикт `{passed, note}`. Без модели — прочерк с советом проверить руками |
| `PlanRunner.kt` | Исполнитель: цикл по `nextPending` (PENDING+FAILED → возобновляемость), прогон агента через `CodingRuntime`, сбор отчёта из событий, вердикт, живые `onUpdate` (статусы ACTIVE/DONE/FAILED сразу в хранилище). Защита: `Mutex` (рантайм однопоточный), `isAborted` между вехами → статус STOPPED. Остановка плана — на первом FAILED |

### Данные (`data/planning/`)

- `JsonPlanningRepository` — ключи `coding-plans` (один план на проект: сохранение заменяет)
  и `model-dossiers` (досье 1:1 к профилю), поверх того же `KeyValueStore`;
- `PlanningStore` — наблюдаемый слой (StateFlow планов и досье), как `SkillStore`:
  плагин наблюдает, исполнитель пишет, интерфейс живёт без ручных обновлений.

### Плагин (`plugins/builtin/CodingPlanningPlugin.kt`)

`MagicPlugin` SPI + `CodingSessionPanel` (новая точка расширения в `plugins/PluginRegistry.kt`:
плагин, поставляющий панель внутрь кодинг-сессии). Панель из двух секций:
- **Досье агентов**: строка на каждый настроенный профиль — описание сильных сторон,
  оценка силы ✦1–5, источник («описано человеком» / «найдено в сети» / «черновик по имени модели»),
  кнопки «Изменить» (ручной редактор) и «Найти в сети» (одноразовый поиск);
- **План задачи**: выбор проекта, поле цели, «Составить план» → черновик (утвердить/отменить) →
  утверждённый план: прогресс-бар, **визуальный график** (цепочка кружков-вех с коннекторами,
  цвет = статус, горизонтальный скролл), карточки шагов (закреплённый агент — выпадающий список,
  «Отчёт и проверка», «Пропустить»), «Выполнить план» / «Прервать выполнение» / «Продолжить после сбоя».

### Экран кодинга: режимы сессии

Включённый носитель `CodingSessionPanel` добавляет в кодинг-сессию вкладки **«Диалог»/«План»**:
диалог с агентом как был, а «План» — та же панель планирования с закреплённым проектом
(без выпадашки выбора). Экран кодинга не знает о плагине: ему передаётся
`UiState.codingPanelPlugin` (первый включённый носитель панели; нет записи состояния = включён).
На экране «Плагины» панель остаётся со свободным выбором проекта.

### Сборка (`di/Dependencies.kt`)

`PlanningStore` собирается рядом со `SkillStore`; плагин получает `PlanComposer`,
`DossierResearcher`, `PlanRunner(codingRuntime ?: NoopCodingRuntime, LlmMilestoneVerifier)`.
На вебе/андроиде — `NoopCodingRuntime`: планирование и досье работают, авто-выполнение
честно сообщает о недоступности.

## Ключевые решения

1. **Агент = профиль подключения**, а не сущность рантайма: пи-агент получает профиль в
   `CodingRuntime.run`, досье привязано к `profileId`. Так выбор «оптимального агента»
   сводится к выбору профиля — без новых сущностей.
2. **Один план на проект** — хранилище само заменяет прежний; история исполнения живёт
   в отчётах и вердиктах мэилстоунов плана (журнал проекта не трогается — раздельные сущности).
3. **Проверяемость зашита в промпты**: композитор просит у модели «что сделать и как проверить»,
   исполнитель передаёт цель+критерий агенту, судья сверяет отчёт с критерием. Цепочка
   замкнута: достижимость проверяется тем же критерием, который был сформулирован при планировании.
4. **Честные фолбэки без модели** (паттерн `SkillEducator`): планировщик, исследователь и судья
   работают офлайн-эвристиками и помечают это в досье/черновике/вердикте.
5. **Возобновляемость**: проваленный шаг остаётся в статусе FAILED и попадает в `nextPending`;
   «Продолжить после сбоя» выполняет только непройденные шаги. Пропуск шага (SKIPPED)
   считается завершением без выполнения.

## Тесты (`commonTest`)

- `JsonPlanningRepositoryTest` — round-trip, замена плана на проект, досье 1:1, повреждённые данные, wipe;
- `AgentMatcherTest` — выбор Кодера/Писателя по тексту шага, оценка как тай-брейкер, игнор ненастроенных;
- `PlanComposerTest` — эвристика без модели, парсинг обёрнутого в ``` JSON, сопоставление агентов, фолбэк при сбое;
- `PlanRunnerTest` — полный прогон с отчётами, остановка на непроверенном шаге, возобновление с FAILED, прерывание.
