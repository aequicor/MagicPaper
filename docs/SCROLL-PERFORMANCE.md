# Лаги скролла на macOS: диагностика 2026-09-08

В работающем MagicPaper найден источник нагрузки в хранении состояния coding agent
и планирования. Это затрагивает весь интерфейс: фоновые события обновляют общий
UiState, а сравнение больших планов выполняется также в потоке интерфейса.

## Измерения до изменения

Снят локальный 25-секундный JFR-профиль процесса `io.aequicor.magicpaper.MainKt`
(PID 76807, macOS ARM64, Zulu Java 21, Compose 1.11.1). В предварительном снимке
процесс потреблял около 140% CPU; дочерний процесс Codex — около 0,1%.

Из 702 выборок исполнения Java:

- 625 (89%) содержали сериализацию JSON или файловое хранилище;
- ещё 48 (6,8%) — глубокое сравнение `CodingStep` и содержащих его объектов;
- в UI-потоке зафиксирована цепочка `CodingStep.equals → StageAttempt.equals →
  Plan.equals → CodingSessionUi.equals → UiState.equals → StateFlow.collect`.

За интервал записаны 307 событий сборки мусора и 384 паузы GC. Суммарная длительность
пауз — 0,537 секунды, самая длинная — 16,9 мс. Это не измерение FPS или задержки жестов.
Размер выделений памяти по весам JFR-сэмплов не использовался для выводов.

Профиль сохранён локально в `/tmp/magicpaper-scroll-before.jfr`; он не отправлялся
во внешние сервисы.

## Механизм и исправление

1. `PlanningStore.planFor()` перечитывал весь архив планов даже для проверки статуса.
   Теперь store загружает планы один раз и обновляет снимок после успешной записи.
   Неизменившиеся планы сохраняют те же объекты, поэтому сравнение не обходит их
   историю заново. Восстановление после ошибки явно перечитывает диск.
2. `JsonPlanningRepository.save()` дважды декодировал тот же архив за одну запись.
   Теперь использует один снимок для текущей и резервной версии.
3. Обновления оркестратора повторно загружали журналы сессий.
   `BackgroundCodingProjectRepository` повторно использует до восьми последних
   списков сообщений. Записи проходят через этот общий экземпляр репозитория;
   удаление, очистка и неопределённый исход записи сбрасывают соответствующий кеш.
4. `monitoredRun()` выдаёт пустой сигнал каждые 100 мс для сохранения последних
   порций ответа. Обработчик принимал тишину за обновление и каждую секунду
   перезаписывал неизменившийся план, запуская повторную публикацию истории.
   Теперь сигнал только допоказывает/сохраняет накопленный текст; после этого
   до следующего события агента нет новых снимков и записей.
5. Обычная coding-сессия обрабатывает поток событий в фоне и публикует текстовый
   снимок не чаще раза в 50 мс. Последняя порция появляется и при последующей
   тишине; границы действий показываются сразу. Сохранённые сообщения и поле
   ввода не пересобираются из-за нового фрагмента рассуждения.
6. Остановка удерживает сессию до завершения очистки рантайма и сохранения
   частичного ответа. Повторный запуск во время остановки не создаёт второй
   прогон, который завершение первого могло бы удалить из состояния UI.

## Бумага и пределы вывода

У бумаги действительно есть полноэкранный шейдер и постоянный кадровый цикл
при активном окне. Кадровое состояние читается в рисовании отдельного слоя,
поэтому само по себе не должно пересобирать чат. GPU-нагрузка и скролл с включённой
и выключенной бумагой отдельно не измерены: профиль Java CPU не исключает
дополнительного вклада анимации. В этой проверке подтверждена нагрузка от состояния
агента; бумага не изменялась.

## Проверка

157 выбранных JVM-тестов прошли без ошибок и пропусков. Сборка и результаты
проверок находятся в `/tmp/magicpaper-scroll-perf-build`, журнал запуска —
`/tmp/magicpaper-scroll-tests.log`.

Регрессионные тесты проверяют тысячу повторных чтений без повторного декодирования,
обновление/удаление истории, ограничение кеша, запись с ошибкой после фактического
сохранения, восстановление плана и проверку ревизий. Тесты исполнения проверяют
отсутствие записей и обновлений во время тишины, показ и сохранение последней порции
текста, завершение и остановку агента. Также выполняются существующие проверки
планирования, скролла чата, отзывчивости UI при занятом backend и отрисовки бумаги.

Перед коммитом выполнена полная повторная проверка:
`./gradlew :shared:jvmTest :desktopApp:compileKotlin :shared:compileKotlinJs :shared:compileKotlinWasmJs`.
JVM: 835 тестов, 0 ошибок, 2 пропуска; desktop, JS и Wasm скомпилированы.
Все 11 Node-тестов в `shared/src/jvmTest/resources/coding/` прошли.
Отдельный прогон `PlanningRuntimeIntegrationTest` с обоими включёнными флагами
подтвердил чтение кода и запрет записи через установленные pi и Codex на локальной
тестовой модели. Регрессия остановки сначала воспроизведена падающим тестом,
после исправления весь `CodingResumeTest` прошёл.

Работающий процесс не заменялся. Для замера улучшения на том же диалоге нужен
запуск свежей сборки после завершения текущей работы агента. Следующая проверка:
сравнить скролл настроек и длинного чата при активном/завершённом агенте,
затем отдельно сравнить анимацию бумаги в одинаковых условиях.
