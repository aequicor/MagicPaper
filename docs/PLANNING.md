# Планирование: дерево решений и исполнение

План проекта хранит цель, диалог уточнений, альтернативы на любом уровне,
выбранные варианты, относительные оценки и назначения исполнителей. В каждый
момент активен один вариант каждой активной точки выбора. Неактивные варианты
сохраняются. Общие этапы исполняются один раз, составной этап готов после всех
выбранных дочерних этапов.

## Работа с планом

1. Откройте «Планирование» или вкладку плана в проекте. Задайте цель.
2. Запустите уточнение и ответьте на вопросы. «Построить варианты» использует
   сохранённый диалог; некорректный ответ модели не заменяет корректное дерево.
3. Выберите вариант в панели узла, уточните критерии и зависимости этапов.
   Оценки качества, скорости, экономичности и надёжности относительные:
   «неизвестно / низкая / средняя / высокая». Веса по умолчанию равны;
   при равном результате предпочтение имеет качество. Ручные выборы сохраняются.
4. Назначьте источник, конкретную модель и доступный effort. Досье хранится для
   пары «источник + модель». Исполнение допускает только модели coding-движка.
5. Нажмите «Утвердить и запустить». Desktop исполняет независимые этапы в
   изолированных Git worktree, по умолчанию два одновременно, настройка 1–8.
   Без Git этапы выполняются последовательно в папке проекта.

Граф строится слева направо: круг «Начало» → задачи → двойной круг «Завершение».
Используется представление activity-on-node: прямоугольник — задача, стрелка —
зависимость. Колонка задачи равна максимальной колонке её предшественников плюс
один. Задачи одного уровня готовности расположены в одной колонке, включая
независимые задачи с разной глубиной вложенности в плане. «Начало» соединено со
всеми задачами без предшественников, все конечные задачи — с общим «Завершением».
Общие задачи показаны один раз. Все стрелки имеют единый плавный стиль;
длинные связи огибают промежуточные карточки без прямоугольных изломов.

По умолчанию видны все альтернативные задачи. На карточках указано название пути;
для вложенных вариантов — цепочка названий. Выбранный путь выделен цветом и
сплошными стрелками, невыбранные пути — приглушёнными карточками и пунктирными
стрелками. Задачи нескольких вариантов помечены «↔ Общая для вариантов».
Легенда под схемой поясняет обозначения. Выбор пути расположен над схемой:
переключатели сохраняют ручной выбор и пересчитывают активные зависимости,
остальные ветви остаются приглушёнными. Это работает в плагине и в схеме плана
в чате, включая вложенные альтернативы. Начатые задачи и общая проверка защищены
от несовместимого переключения. «Выбранный путь» оставляет только активные задачи.
Точки выбора и группы не занимают рабочие колонки.

Сложность задаётся в условных единицах (например, 1, 2, 3, 5, 8, 13), вручную или
планировщиком. Для старых планов применяется имеющаяся оценка сложности 1–3,
если новая не задана. Оценки времени не переводятся в сложность автоматически.
Граф показывает сложность каждой задачи в условных единицах. Это относительная
сложность, а не часы и не срок завершения. Отсутствие оценок не мешает видеть зависимости и выбирать варианты.
Основа графа зависимостей: [Critical path method](https://en.wikipedia.org/wiki/Critical_path_method).

Граф поддерживает масштабирование, перемещение, выбор задачи и
«Показать целиком». Клавиатура: Tab — фокус, Enter — действие, стрелки — перемещение,
Home — весь граф. Стрелки показывают зависимости, приглушённые карточки — невыбранные альтернативы.
Статусы имеют текст и символы. На широком экране диалог расположен рядом,
на узком — в переключаемой панели. Панель узла содержит критерии, оценки,
назначение и журнал попыток; служебные проверки и конфликты видны на графе.

Можно редактировать будущие этапы. Начатые этапы, их зависимости, модель и effort
закреплены. Ответ планировщика допускает обновления отчётов за время запроса,
но не перезаписывает параллельные ручные изменения. Во время общей проверки
структура текущего запуска закреплена. Если итоговый результат отклонён,
в той же сессии можно добавить этапы продолжения. Завершённые этапы сохраняются,
предыдущая итоговая проверка переносится в историю, а после новых этапов запускается
новая проверка. Уточняющий вопрос или изменение подписи не снимает блокировку.

## Исполнение и рабочие копии

`DecisionCompiler` отделяет дерево решений от DAG исполнения. Проверяет ссылки,
циклы, выбор альтернатив, неактивные зависимости и общие этапы.
`PlanningExecutionService` принадлежит приложению, запускается из DI и не зависит
от открытого экрана. `PlanningStore` последовательно применяет команды и события
с проверкой ревизии. Старые планы мигрируют в один выбранный вариант, сохраняя
этапы, отчёты, зависимости и идентификаторы сессий.

`GitPlanningWorkspace` создаёт снимок текущих файлов через отдельный Git index,
сохраняя исходные HEAD, index, незакоммиченные и новые неигнорируемые файлы.
Git-проект открывают от корня репозитория. Этап получает рабочую копию и отчёты
зависимостей. Проверенные коммиты объединяются последовательно. Конфликт имеет
собственную сохранённую фазу, конфигурацию, сессию, отчёт и до двух исправлений.

Общая проверка запускает подходящие проверки объединённого результата. Агенту
проверки запрещено менять код, а порт проверяет отсутствие изменений отслеживаемых
файлов. Затем отдельная копия переноса объединяет результат с текущими
пользовательскими правками. Перед записью проверяются хеши каждого исходного файла.
Рабочие копии сохраняются после переноса для диагностики и восстановления.
Символьные ссылки и submodule при переносе требуют ручной проверки.

Pi использует отдельные settings/models.json для каждой сессии; параллельные
назначения не меняют общий файл. Попытка закрепляет модель и effort независимо
от coding-настроек профиля. Неподдерживаемый effort блокирует выполнение.

## Автоматическое восстановление

Намерение пользователя (`RUN / PAUSE / STOP`) отделено от фазы выполнения.
После старта приложения активные планы продолжаются без открытия панели.
Пауза и остановка сохраняются. Пауза прекращает выдачу новых работ, остановка
прерывает активные сессии. Штатное закрытие останавливает исполнителей, оставляя
намерение автоматического продолжения.

Перед созданием копии, агентом, объединением и переносом записывается намерение.
Запуск, этап, попытка, сессия, конфигурация, фаза, отчёты и повторы входят в
контрольную запись проекта. Хранилище сохраняет текущий и предыдущий снимки;
индекс восстанавливается по контрольным записям, включая записи удаления.
Файловая запись использует временный файл, синхронизацию и атомарное переименование.
Повреждение единственной записи проекта не считается отсутствием плана.

Границы операций сохраняются сразу, потоковый текст — не реже раза в секунду,
основная трансляция текста в UI — с шагом до 100 мс при поступлении событий.
Ошибка хранилища прекращает исполнителей и новые изменения; продолжение возможно
после повторного чтения подтверждённого состояния и успешной пробной записи.

На проект и хранилище исполнения удерживается межпроцессная блокировка.
При восстановлении идентичность процесса сверяется по PID и времени старта,
учитывается владелец приложения. Если подключение к прежнему исполнителю не
поддерживается, принадлежащий запуску процесс завершается перед продолжением.
Windows дополнительно использует Job Object: аварийное завершение приложения
закрывает агента и его дочерние инструменты. Нативная проверка этого механизма
включена в JVM-тесты Windows. На macOS проверено принудительное завершение
процесса владельца и последующее восстановление: записанный агент и его дочерний
инструмент завершаются, запись владения удаляется. Это проверка восстановления,
а не гарантия немедленного завершения инструментов при падении macOS-приложения.
На Linux этот сценарий пока не запускался.

Подтверждённая работа не исполняется повторно. Фаза проверки возобновляет проверку;
объединение сверяет коммиты и незавершённый merge. Даже уже созданный агентом
merge-коммит не обходится без сохранённого результата проверки. Перенос имеет
манифест с хешами «до / после» и продолжает частично применённые изменения.
Если пользователь изменил файл после подготовки переноса, запись блокируется.

## Ошибки

| Ситуация | Действие |
|---|---|
| Временная сеть, 429, 5xx | До трёх повторов: 2, 5, 15 секунд + разброс, с учётом Retry-After |
| Невалидный ответ планировщика/проверяющего | До двух исправлений JSON с конкретной диагностикой |
| Авторизация, источник, модель, effort, папка | Сохранённая блокировка, повторная проверка после исправления |
| Проверка результата не прошла | До двух исправлений в той же рабочей копии |
| Конфликт | До двух исправлений с проверкой; затем решение пользователя |
| Прерванный поток или процесс | Сверка владельца, сессии и файлов перед продолжением |
| Неизвестный результат внешней команды | Решение пользователя; новый исполнитель не стартует |
| Диск/повреждение данных | Остановка изменений до восстановления рабочего хранилища |
| Пауза/остановка пользователем | Автоматические повторы не возобновляют план |

Лимиты повторов и сроки записаны в попытке и не обнуляются перезапуском.
Для исключений до создания попытки счётчик хранится в плане. Исключения
проверяющего сохраняют фазу проверки и не запускают реализацию заново.
Незавершённые внешние команды итоговой проверки также требуют подтверждения.
Пустой отчёт, ошибка движка и недоступный проверяющий не означают успех.
После отклонения итогового результата кнопка «Доработать план» возвращает задачу
планировщику с причиной отказа и сохранённым диалогом, включая ещё не применённые
запросы пользователя. Новые этапы продолжают запущенный план; явная пауза или
остановка сохраняется. При недоступности проверяющего повторяется сама проверка.
Таймаут берётся из профиля; длительная работа инструмента сама по себе не
считается зависанием. Из диагностик удаляются известные ключи подключения,
Authorization и параметры секретов.

## Проверки

`./gradlew :shared:jvmTest :shared:compileKotlinJs :shared:compileKotlinWasmJs :androidApp:assembleDebug :desktopApp:compileKotlin`

Автоматические тесты охватывают DAG/альтернативы, общие этапы, цикл неактивной
ветви, закрепление начатого этапа, настройку модели, параллельный старт и зависимости,
паузу/остановку, возобновление проверки и конфликта, ограниченные повторы,
повреждённые снимки, отказ сохранения, владение процессами, сохранение Git index,
пользовательские правки, стабильный коммит после сбоя, прерванное создание копии
и частичный перенос. Compose-тест рисует граф на широком/узком экране и 200 узлов,
проверяет выбор узла; изображения — `shared/build/reports/planning/`.

Тесты исполнителя используют управляемые локальные движки. Удалённые Pi/Codex
с авторизацией и реальными моделями в этом наборе не вызываются; отдельные
интеграционные тесты проекта включаются явно. Реализация доступна в Desktop,
планирование и редактирование — также в Web и Android.
