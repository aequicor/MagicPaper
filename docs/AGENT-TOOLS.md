# Инструменты агентов

MagicPaper использует Command для вызовов приложения и Observer для истории выполнения.
Роль, режим и контекст задаёт приложение. Модель получает только доступные определения
инструментов и их аргументы. Для pi создаётся расширение, для Codex — локальный MCP-сервер
`magicpaper_agent_tools`. Общие wire-имена: `magicpaper_` + ID с заменой точек на `_`.

| ID | Возможность | Роли |
| --- | --- | --- |
| file.read, file.search, file.list, git.inspect | Чтение, поиск, структура, просмотр Git | Все |
| context.get, web.search | Состояние своего проекта/плана, поиск источников | Все |
| session.create, session.send, session.control, session.wait | Дочерние сессии, контекст и жизненный цикл в пределах полномочий | Все обычные сессии |
| session.route, session.result.review, session.result.get | Разрешённый маршрут между ветками, приёмка и чтение принадлежащих сессии результатов | Все обычные сессии |
| session.results.integrate | Интеграция принятых результатов детей с фактическими итоговыми проверками | Обычные сессии в CODE |
| session.integration.get | Чтение сохранённой интеграции и вывода проверок по частям | Автор интеграции или иммунитет организма |
| immunity.signal, receipt.get | Диагностический сигнал и чтение сохранённых квитанций | Все обычные сессии |
| questionnaire | Опросник, ожидание подтверждённых ответов | Все |
| plan.propose | Передача проверяемого проекта плана | Планировщик |
| plan.refine, plan.recalculate | Разработка плана, пересчёт выбранного поддерева | Оркестратор |
| plan.control | Пауза, остановка, продолжение, повтор, подтверждение | Оркестратор |
| stage.pause, stage.send, stage.resolve | Выборочная пауза, задания, решение по результату | Оркестратор |
| session.manage | Создание, переименование, архивирование, восстановление | Оркестратор |
| schedule.manage | Создание, изменение, отмена отложенных сообщений | Оркестратор |
| stage.handoff | Результат, вопрос, блокировка, запрос ожидания | Исполнитель текущего этапа |
| file.edit, file.write, shell.exec, computer | Изменения, команды, управление компьютером | Рабочие сессии в обычном режиме |
| research_check | Защищённые проверки | Рабочие сессии в режиме исследования |

Файлы и shell выполняет выбранный движок. Адаптер сопоставляет его события с каталогом;
получение события не выполняет операцию ещё раз. Codex может читать файл через shell:
в этом случае история честно показывает команду. Его песочница чтения и разрешения pi
сохраняются. Управление компьютером по-прежнему требует отдельного разрешения сессии.

## Исполнение

`ToolDefinition` задаёт схему, роль и категорию. `ToolRegistry` перечисляет команды,
`ToolCommand<Args, Result>` инкапсулирует вызов, `ToolExecutor` проверяет аргументы и
контекст, фиксирует квитанцию и вызывает получателя. `ToolHost` связывает команды с
существующими сервисами и создаёт отдельный `ToolSession` для каждого запроса.

`ToolExecutionContext` передаётся через контекст корутины, в том числе через `flowOn`.
Он содержит владельца чата, проект, запрос, роль, режим, план, запуск и попытку этапа.
Аргументы инструмента не могут переопределить эти значения. Проверки доступа работают
как при перечислении инструментов, так и на сервере при вызове.

Планировщик передаёт данные через `plan.propose`, исполнитель — через `stage.handoff`.
Обычный ответ остаётся текстом для пользователя. Схема предложения содержит только
редактируемые поля; попытки выполнения, сохранённые разрешения и статусы модели не выдаются.
Валидация предложения использует тот же компилятор дерева и реестр критериев приёмки.
Передача RESULT сохраняется до следующего участника и сама по себе не принимает этап:
приёмку и фактические проверки выполняет приложение. Доказательства берутся из передачи,
даже если окончательный текст исполнителя краткий.

Продолжение, повтор и подтверждение плана требуют пользовательского источника запроса;
автоматическая доставка не может снять пользовательскую остановку. Существующие проверки
ревизии, вопросов, предложения и принадлежности сессий остаются обязательными.

## Интеграция результатов универсальных сессий

`session.results.integrate` принимает `resultIds`, `checks` и необязательный `expectedVersion`.
`resultIds` — от 1 до 32 различных сохранённых результатов; `checks` — от 1 до 8 команд,
каждая задана массивом аргументов. Секреты в аргументах проверок отклоняются до записи.
Пути исходников, их фактический снимок, проект, организм, автор и поколение берутся
из контекста приложения. Интеграция разрешена только обычному runtime в CODE; временный
проверяющий алиас не получает это право. Результаты должны быть приняты ответственным
родителем, принадлежать его непосредственным завершённым детям и текущим поколениям,
иметь подтверждённые SHA, снимки и выделенные рабочие копии. Чужая ветка или режим
чтения не могут расширить полномочия аргументами вызова.

До Git и проверок одна транзакция организма сохраняет неизменяемый `SessionIntegrationRequest`,
операцию и аудит. Запрос фиксирует упорядоченный состав результатов, команды, авторство,
поколение и исходный снимок. Fingerprint вычисляется по исходным каноническим аргументам
инструмента, включая явно указанную версию. Тот же operation ID с другими результатами,
порядком, проверками или `expectedVersion` отклоняется; точный повтор читает сохранённую
интеграцию. Неуказанная версия проверяется при каждом допуске, с ограниченным повтором
только доказанного конфликта до записи. Checkpoint не может заменить запрос или записать
результат отозванного поколения.

Интеграция использует существующий `PlanningWorkspace`: отдельную Git-копию, общий контроль
писателей и сериализацию операций с refs. Перед объединением сверяются снимки источника
и результатов. Команды итоговой проверки выполняет существующий защищённый
`ResearchCheckRunner`, без обходного неограниченного запуска. Сохраняются фактические
аргументы, exit code, вывод и причина блокировки каждой проверки; секреты маскируются
до сохранения и передачи. Проверяемый снимок сравнивается после проверок и Git capture.

| Фаза | Подтверждённый смысл |
| --- | --- |
| INTENT | Состав и намерение сохранены; внешний результат ещё не доказан |
| PREPARING, MERGING, VERIFYING | Подготовка, объединение или итоговые проверки продолжаются |
| CONFLICT | Обнаружен конфликт; рабочая копия сохранена |
| BLOCKED | Проверка или допуск не позволили подтвердить результат |
| VERIFIED | Объединение, проверки, SHA и завершение владения рабочей копией подтверждены |
| UNKNOWN | Исход эффекта либо завершение проверки/освобождение копии не подтверждены |

Краткий ответ содержит `integrationId`, `phase`, `verified`, рабочий путь, SHA, снимок,
ошибку, число проверок и ID результатов. Завершённая команда с `CONFLICT` или `BLOCKED`
не означает принятую интеграцию: `verified` остаётся `false`. Полную сохранённую запись
читает `session.integration.get(integrationId, offset, limit)`, где `limit` — от 1 до
16 000 символов. Ответ включает `totalCharacters`, `offset`, `content` и `truncated`.
Чтение проверяет проект, организм, поколение и принадлежность автору либо иммунитету;
оно не запускает проверки повторно. Пользовательский HEAD, index и рабочая папка этим
инструментом не переключаются и не перезаписываются; результат остаётся отдельным артефактом.

При завершении дочерней CODE-сессии приложение может включить в её результат уже проверенную
интеграцию внуков. Выбирается последняя совместимая VERIFIED-интеграция этого автора и
поколения, чей исходный снимок совпадает с окончательным снимком собственных файлов сессии.
`SessionResult.integrationId` связывает результат с точными интеграционными SHA, снимком,
путём и фактическими проверками. Более поздние изменения собственных файлов исключают
автоматический выбор устаревшей интеграции. Синтезируемое представление результата сохраняет
исходный путь и base commit рабочей копии родителя: следующий предок интегрирует полный
результат своей ветки. Оригинальная запись владения рабочей копией не заменяется.
Уже сохранённый `integrationId` никогда не подменяется более новой интеграцией.

Сбой между намерением, Git, проверкой и checkpoint оставляет самостоятельный UNKNOWN.
После перезапуска незавершённые интеграции получают UNKNOWN и карантин с аудитом.
Восстановление прекращает и сверяет процессы проверок, освобождает подтверждённое владение,
но не повторяет merge, проверку или capture. Сверка квитанции может вернуть только уже
доказанные VERIFIED/BLOCKED/CONFLICT при совпадении автора, поколения и fingerprint;
она не снимает карантин. Общая ACID-транзакция с Git и процессами не заявляется.

## Предложения и вмешательства иммунитета

`immunity.signal` остаётся узким каналом диагностики, доступным независимо от состояния
родителя. Приложение пробуждает пассивный иммунитет по событию. Жалоба сама по себе не
создаёт предложение вмешательства: нужны сохранённые наблюдения, например подтверждённая
ошибка runtime, неизвестный исход, исчерпанный бюджет или зависшая операция.
Диагноз связан с поколением; старый диагноз без поколения остаётся историей и требует
нового сигнала для выдачи полномочий. Автоматическая проверка может сохранить карантин
и остановить затронутую область без LLM-цикла.

В `ImmunityIntervention` сохраняются ID сигнала и предложения, цель, поколение, основания,
затронутая область, разрешённые действия, выбранное действие и время подтверждения.
Состояния — PROPOSED, ACCEPTED, COMPLETED, REJECTED и UNKNOWN. В сессии иммунитета
пользователь рассматривает основания и подтверждает PAUSE, QUARANTINE, STOP, ARCHIVE,
RECREATE либо DELETE_HISTORY. Это отдельный путь приложения
`approveImmunityIntervention`, а не право обычной модели обходить родство или получать
человеческое согласие из текста. Отклонение сохраняется через `dismissImmunityIntervention`.
Пользовательская остановка иммунитета запрещает новые допуски; подтверждённые ограничения
и безопасная остановка не зависят от его дальнейшей работы.

Перед пересозданием проверяются поколение, завершение всего поддерева, актуальность правил,
отсутствие уже принятой работы и неизвестных эффектов. Проверка квитанций охватывает все
запросы владельцев, включая native-buckets; адаптер без полного обхода не доказывает
безопасность. Незавершённая интеграция в агрегате также блокирует восстановление, даже
если её квитанция не успела сохраниться. Ресурсы берутся из существующего резерва иммунитета,
действуют лимит повторов и минутный интервал между пересозданиями. Ребёнок требует живого
родителя и совпадения фактических исходников с заданием. Старые попытки плана проходят
подтверждённый плановый путь, а не универсальный повтор native-запуска. Зигота получает
новое поколение в PENDING для нового запроса пользователя; прежний native-контекст
очищается и старое поручение автоматически не исполняется.

DELETE_HISTORY требует второго явного подтверждения с перечислением удаляемой области;
для зиготы она включает независимый иммунитет. Сначала сохраняются выбранное действие,
подтверждение и намерение остановки, затем существующий путь удаления подтверждает
завершение и сохраняет tombstone. История не считается удалённой по одному checkpoint
остановки. Обязательный аудит и само предложение остаются в агрегате. Состояние UNKNOWN
или повторное подтверждение допускают только проверку сохранённого результата: приложение
не запускает пересоздание и не вызывает удаление второй раз вслепую.

## Наблюдение и восстановление

`ToolEventHub` публикует STARTED, PROGRESS, WAITING, SUCCEEDED, FAILED, CANCELLED и UNKNOWN.
Наблюдатель преобразует их в существующие `CodingEvent`/`CodingRunRecorder` и сохраняемые
`CodingStep`. Карточка обновляется на месте. Ожидание ответа и отмена имеют отдельные
состояния; незавершённый инструмент не становится успешным при закрытии потока.
Ключ карточки определяется вызовом и сохраняется при переносе из временного ответа в
историю. Вложенный планировщик не заменяет активную карточку команды оркестратора;
уже сохранённые вызовы исключаются из живого ответа без потери остальных вызовов.
Предпросмотр аргументов ограничен. Секреты маскируются в структурированных аргументах,
результате, ошибке и заголовке до сохранения и передачи наблюдателям. Ключи подключений
дополнительно передаются через `ToolHost.knownSecrets`; обработчик команды получает
исходные аргументы, а сохранённая история и ответ модели — разрешённое содержимое.

Подробности остаются в чате вызывающей сессии. Временный контекст планировщика связан с
родительским чатом; оркестратор получает передачу задания и результаты исполнителей.
События собственных инструментов от движка подавляются только для точно объявленных
имён: источником их жизненного цикла является исполнитель команд. Остальные MCP-вызовы
Codex также видимы в истории.

Квитанции сохраняются отдельно от отображения для вызовов приложения, включая чтение,
опросники и отклонённые обращения. Их ключ включает проект, владельца, запрос и call ID.
Одно атомарное резервирование допускает только одного исполнителя этого идентификатора.
SHA-256 канонических аргументов вычисляется до маскирования: повтор с другим инструментом
или аргументами отклоняется, даже если отличаются только скрытые секреты. Порядок ключей
JSON-объекта не меняет идентичность. Подтверждённую квитанцию нельзя вернуть в STARTED
или заменить её результат. Повтор завершённого вызова возвращает сохранённый результат.
После сбоя сервис сверяет
незавершённую квитанцию с записями доставки, сессий, расписания, передачи результата или
сохранённого предложения. Если факт завершения не доказан, повтор блокируется.
UNKNOWN отличается от подтверждённого отказа: исключение или отмена ожидания после начала
изменяющего вызова не доказывает отсутствие внешнего эффекта. Новый call ID не обходит
блокировку последующих изменений в том же запросе. `unknownOutcome` передаёт приложению
основание для карантина сессии; `authorizeTool` проверяет полномочия до выполнения и
повтора. Чтение истории и канал `immunity.signal` остаются доступны при блокировке.
Проверки `requireTool`/`checkTool` обозначают только подтверждённый отказ до эффекта
либо после проверенной безопасной компенсации. Произвольное исключение таким отказом
не считается. Контекст поколения и правил фиксируется `contextDefaults` один раз при
создании `ToolSession`; старый экземпляр не получает новые полномочия автоматически.

У изменяющих инструментов `session.*` и `immunity.signal` есть необязательный
`expectedVersion`: это `organismVersion` из `context.get`, версия всего сохранённого
организма, включая outbox и бюджет. Явно указанная устаревшая версия отклоняется
в той же транзакции, которая сохраняет команду. Если поле опущено, мост приложения
снимает текущую версию отдельно для каждой отправки и проверяет её при записи;
при типизированном конфликте до записи повторяет только транзакционную проверку
с текущей версией (до четырёх попыток), сохраняя команду и снятую версию исходников.
Явную модельную версию приложение не заменяет. Один `ToolSession` может последовательно выполнять несколько команд. Поколение
runtime при этом остаётся фиксированным. Явная версия входит в идентичность команды:
точный повтор после изменения состояния возвращает сохранённую операцию, а тот же
operation ID с другой версией или аргументами отклоняется.

`authorizeCommand` проверяет аргументы до выполнения, повторного чтения результата
и пользовательских override-обработчиков. Старые инструменты планов допускаются
только у действительного родителя плана; адресуемые сохранённые сессии этапов должны
быть его непосредственными детьми. `stage.handoff` сохраняет обращение ответственному
родителю и сам не доставляет сообщения соседям. Временные runtime объединения и
итоговой проверки сохраняют прежнего владельца истории, но не получают его полномочий
создания или управления сессиями. Диагностические чтения и сигнал иммунитету доступны.
Проверка поколения повторяется после ответа изменяющего инструмента и перед записью
нативного события; поздний результат не превращается в актуальный успех.

Для существующей квитанции после точного совпадения идентичности применяется отдельный
`authorizeReceipt`: он проверяет владельца и поколение, но не возвращает право выполнять
новые изменения. Это позволяет доказать исторический результат в карантине. Сверка
`session.*` восстанавливает нормализованную команду из сохранённых аргументов и требует
совпадения fingerprint с операцией и её аудитом в организме. Создание требует подтверждённого
запуска либо известного терминального наблюдения, передача — DELIVERED/PROCESSED,
остановка и ожидание — подтверждённых терминальных состояний. Приёмка, маршрут,
переименование и сигнал требуют собственных сохранённых доказательств. Принятое намерение
само по себе не доказывает внешнего результата. Сверка не запускает runtime, не доставляет
контекст повторно и не снимает карантин. Если маскирование мешает воспроизвести fingerprint,
исход остаётся неизвестным; нативные/Git-эффекты эта сверка не повторяет.

Для уже управляемых организмом сессий старый `session.manage` не переименовывает,
не архивирует и не восстанавливает проекции напрямую: отказ предлагает `session.control`.
Проверка находится также в адаптере сохранённых решений; он не создаёт полномочия текущего
поколения для старой команды. Неисполненная команда сохраняется с `error`, а связанное
сообщение TOOL объясняет отказ. Повтор восстанавливает это сообщение, не повторяя действие.
Переименование явным контролом пользователя проходит отдельную транзакцию организма
с USER-аудитом и не меняет поколение, рабочее состояние или бюджет. Новые поля `error`
и `nameManuallySet` читаются со значениями по умолчанию. Контекст рабочей сессии содержит
только её текущий этап; изменяемые отчёты соседей доступны ответственному родителю.

`context.get` показывает квитанции текущего запроса, чтобы восстановленный агент учитывал
уже выполненные действия; `receipt.get` читает разрешённое сохранённое содержимое по частям.
`resultReferences` содержит последние 30 результатов, созданных сессией или назначенных
ей для проверки, а `resultReferencesOmitted` — число остальных. У иммунитета областью
проверки является организм. Ссылки содержат только ID, источник, поколение, приёмку,
версию исходников и commit SHA; полное содержимое читает `session.result.get`.
Ссылки доступны независимо от отмены доставки результата.
Большой результат приложения хранится полностью после маскирования; сокращённый
предпросмотр содержит признак сокращения и идентификатор квитанции.
Нативные события также сохраняются, но движок часто передаёт только описание и
предпросмотр. Поэтому их `argumentsComplete` и `resultComplete` равны `false`: отсутствующие
аргументы не восстанавливаются из текста. Без native call ID квитанция не выдумывается.
При завершении потока без результата начатый нативный вызов получает UNKNOWN до
завершения общей истории. Ошибка наблюдателя не выполняет команду повторно.

Транзакционная граница квитанций — замена одного request-bucket в `KeyValueStore`.
Экземпляры `StoredToolReceipts` синхронизируются внутри одного процесса приложения;
десктопное хранилище заменяет файл атомарно. Эта граница не включает состояние организма,
Git, файловые изменения или внешние API и не является блокировкой между процессами.
Сначала сохраняется намерение, затем выполняется действие, затем сохраняется результат.
Потеря записи результата оставляет отдельное основание для сверки, а не разрешение повторить
действие. Нативная история является наблюдением и не даёт механизма повторного выполнения.

Старые `UserTurnDecision`, `CoordinatorReply` и `StageReply` читаются с прежними значениями
по умолчанию. Выполняемые сохранённые решения проходят через адаптер команд с сохранением
старых идентификаторов действий. Исторический текст сообщений не интерпретируется как
новый вызов инструмента. Новые поля жизненного цикла, происхождения передачи и запроса
пересчёта необязательны при чтении старых сохранений.
Старые квитанции читаются с прежними идентификаторами и результатами. При обращении к
bucket их исходные аргументы сначала получают fingerprint, затем секреты маскируются
и bucket сохраняется. Новые поля имеют значения по умолчанию; старые квитанции считаются
изменяющими, поскольку прежняя версия сохраняла только такие вызовы.

Таймаут запуска планировщика, состояние прерванных рабочих сессий и удержание пауз
после ошибки доработки описаны в [PLAN-CHANGE-DEFECTS.md](PLAN-CHANGE-DEFECTS.md).
