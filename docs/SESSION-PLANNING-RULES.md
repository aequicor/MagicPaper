# Методика планирования и рабочие копии

Редакция реализации: 2026-09-10. Этот документ описывает выполненные изменения и их границы; он не является подтверждением полной приёмки всей инфраструктуры сессий.

## Версии, область настройки и наследование

`domain/PlanningRules.kt` отделяет методику от обязательной политики приложения:

- `PlanningRulesSettings` хранится в `AppSettings.planningRules`. Область настройки — новые запуски во всех проектах приложения.
- `customPrompt = null` выбирает поставляемую методику `DEFAULT_PLANNING_RULES`; версия поставки задаётся `DEFAULT_PLANNING_RULES_VERSION`.
- `edited()` изменяет редакцию только при изменении нормализованного текста; пустая редакция означает стандартную методику. `reset()` возвращает стандартный текст.
- `snapshot()` сохраняет текст, версию, источник и редакцию настройки в `PlanningRulesSnapshot`. Снимок содержит сам текст, поэтому сохранённый запуск не зависит от последующего изменения настройки или поставляемого текста.
- `effectivePrompt()` дополняет снимок описанием обязательных границ. Этот текст объясняет ограничения, но не реализует проверки полномочий: их выполняют host, хранилище состояния и runtime.

`Plan.planningRulesSnapshot` и `CodingSession.planningRulesSnapshot` сохраняют редакцию запуска. `PlanningExecutionService.start()` фиксирует её вместе с намерением запуска до исполнения; этапы и сессии проверки/разрешения конфликтов получают тот же снимок. `SessionOrganismStore` сохраняет правила в узле сессии, а создаваемые дети наследуют снимок непосредственного родителя. Изменение настроек не меняет сохранённый снимок работающего организма.

`PlanComposer` передаёт снимок через `ToolExecutionContext` и `PlanningRulesContext`; второй канал нужен внутренним вызовам без tool host. `RuntimePlanningGateway` переносит его в временную сессию чтения проекта. `CodingSystemPrompts`, `DesktopCodingRuntime`, `PiCodingRuntime` и `CodexAppServerOpenAiSubscription` используют сохранённый снимок и в фактическом промпте, и при просмотре контекста. В режиме планирования инструкции режима чтения остаются отдельной обязательной частью промпта, а защищённый маршрут runtime сохраняется.

В `SettingsScreen.PlanningRulesSettingsSection` доступны редактор, возврат к стандартной методике и просмотр эффективных правил. Изменения вступают в силу после общего действия «Сохранить настройки». Секция использует существующие публичные Paper-компоненты; собственного интерактивного примитива вне `:designSystem` не добавлено.

## Что определяет методика

Стандартный промпт задаёт исследование исходников, декомпозицию по проверяемым результатам, делегирование, принадлежность результата, критерии milestone и рабочую Git-стратегию. Для разрешённой разработки он предлагает feature-ветки, отдельные worktree для независимых потоков изменений, содержательные коммиты, SHA и результаты проверок. Исследование само по себе не требует рабочей копии. Checkpoint и принятый milestone различаются; отсутствие изменений не требует пустого коммита.

Из `PLANNING_INSTRUCTIONS` удалены дубли методики, оставлены ограничения режима и формата. `PlanComposer.COMPOSE_PROMPT` больше не требует фиксированных 2–6 этапов. `DecisionPlanner` больше не предписывает каждому новому плану отдельный этап «Коммит и итог». Новые планы не получают его автоматически через `withFinalization()`; уже существующие итоговые этапы сохраняют свой контракт зависимостей при редактировании. Проверки схемы, допустимости критериев приёмки и неизменности начатой работы остаются в коде.

Это выборочное устранение конфликтов методики. Старые типы ролей, планов, назначений и вспомогательные пути оркестрации продолжают существовать ради совместимости; вся прежняя модель оркестратора не удалена. Пользовательский промпт также не означает поддержку произвольного Git-механизма: безопасные операции выполняются через реализованный `PlanningWorkspace`.

## Git: поведение и гарантии

Изменения находятся в `data/planning/GitPlanningWorkspace.kt`:

- `prepare()` создаёт именованную интеграционную feature-ветку через существующий механизм Git worktree. `stage()` создаёт отдельную ветку и worktree для потока изменений. Имена имеют вид `codex/magicpaper/<назначение>-<хеш пути>` и не конфликтуют между рабочими копиями.
- Уже сохранённые detached worktree открываются без изменения. Нового параллельного хранилища результатов не создано: `workspace.json`, исходная база, манифест переноса и `refs/magicpaper/<attempt>` сохраняют прежнее назначение.
- `snapshot()` использует временный приватный index. Чистая рабочая папка с существующим HEAD использует его SHA. Снимок грязной исходной папки явно называется checkpoint существующей работы, а не принятым milestone.
- `capture()` также использует приватный index и не меняет пользовательский index. Результат определяется относительно сохранённой базы этапа: исходные пользовательские изменения остаются частью базового checkpoint, а не дополнительными изменениями milestone.
- При отсутствии изменений `capture()` возвращает базовый SHA без пустого коммита. Если агент уже создал коммит с актуальным деревом, используется его SHA; история не сплющивается и коммит не дублируется. Незакоммиченные изменения фиксируются поверх текущего HEAD, продолжающего базу этапа. Тема берётся из названия этапа, переданного сервисом выполнения.
- Стабильная ссылка `refs/magicpaper` записывается через compare-and-swap. Повтор фиксации возвращает сохранённый результат только при совпадении дерева; изменившаяся рабочая копия требует отдельного решения. Приложение не перезаписывает прежнюю квитанцию.
- `serializedMutation()` сериализует фиксацию, интеграцию и перенос для одной рабочей копии внутри процесса. Существующие файловые блокировки `acquire()`/`release()` сохраняют владение хранилищем и проектом. Приложение отказывает Git-операциям фиксации и интеграции для путей вне своего хранилища.
- Режим `sharedWorkspace` использует тот же `acquire()`/`release()`, поэтому отдельные планы не обходят аренду единственного писателя. Локальный адаптер резервирует путь под mutex; другой идентификатор проекта с тем же путём не получает вторую аренду и не может освободить чужую.
- Git-адаптер связывает аренду с идентификатором и каноническим путём. При сбое `release()` запись и дескрипторы сохраняются до успешного завершения очистки; повтор пропускает уже освобождённые OS-блокировки. Пока очистка не подтверждена, псевдоним пути не обходит оставшуюся запись, а недействительный дескриптор владельца хранилища не разрешает новый запуск. Освобождение аренды исходной папки не освобождает отдельную аренду исполняющей рабочей копии.
- Интеграционная ветка получает результат через проверяемое объединение. Фиксация через Git plumbing сама по себе не передвигает HEAD рабочей копии этапа; авторитетный SHA результата находится в квитанции и `refs/magicpaper`. Пользовательский HEAD и staging area исходного проекта не переключаются.
- Перенос в исходную папку сохраняет манифест и хеши файлов, проверяет весь набор до записи и повторно проверяет каждый файл. После прерванного переноса уже применённые файлы распознаются, новые пользовательские правки отклоняют продолжение. Конфликтующие worktree сохраняются для проверки и разрешения.
- Папка без Git остаётся без репозитория: `git init` не выполняется. Сервис выполнения сериализует работу в такой папке и сообщает об ограничении. Эти изменения не добавляют удаления worktree при архивировании.

## Транзакционные границы и ограничения

Снимки правил — обычные сериализованные поля соответствующей сущности; они не образуют общую транзакцию между планом, проектной историей, Git и runtime. Для нового агрегата сессий `SessionOrganismStore` сохраняет состояние, операцию, аудит, outbox и резервирование бюджета одной заменой ключа. Атомарность и долговечность этой замены зависят от реализации `KeyValueStore`. История и список сессий являются отдельными восстанавливаемыми проекциями.

Git и файловая система не входят в эту транзакцию. Здесь используются сохранённые базы и намерения, стабильные ссылки, проверка фактического дерева, манифест переноса и повторяемые операции. Коммит не является решением о приёмке. Проверка результата остаётся обязанностью сервиса выполнения.

Остаются существенные ограничения:

- Хеш-проверка перед заменой файла не является блокировкой внешнего редактора: между последней проверкой и атомарным переименованием существует файловая гонка. Общая ACID-гарантия для пользовательской папки не заявляется.
- `GitPlanningWorkspace.reconcile()` проверяет наличие рабочей копии; сам по себе этот метод не доказывает завершение ранее запущенного процесса Git. Владение и завершение native-процессов требуют отдельной сверки runtime.
- Прямому CODE-потомку требуется изолированная рабочая копия через `SessionCodingWorkspaces`. При отсутствии Git или адаптера изоляции запуск отклоняется приложением. Native-выход, неизменность снимка при фиксации и освобождение аренды проверяются отдельно; неизвестный исход сохраняет аренду для последующей сверки.
- Выполненные JVM-тесты не подтверждают поведение настоящих Pi/Codex-сервисов, операционных систем после аварийного завершения питания или нативную доступность интерфейса Windows.

## Миграция

Старые сериализованные настройки получают `PlanningRulesSettings()` по умолчанию. Старые планы и сессии без снимка читаются с `planningRulesSnapshot = null`, без удаления истории. Для уже начатых планов с сохранённым `runId` или попытками при доработке/возобновлении фиксируется стандартная методика с источником `LEGACY`, а не незаметно применяется текущая пользовательская редакция. Ранее сохранённые снимки всегда имеют приоритет. Старые итоговые этапы и detached worktree продолжают работать по прежним идентификаторам.

Явное удаление истории сохраняет `SessionOrganism.historyDeletedIds`, а удаление зиготы/целого организма также `deletedAt`. Сервис сначала отменяет и дожидается владельцев runtime и планов; `deleteHistoryByUser()` требует подтверждённого завершения всех затронутых узлов. После этого одна запись агрегата отзывает поколения, сохраняет аудит и отменяет недоставленный outbox. Удаление журналов остаётся отдельной восстанавливаемой проекцией: после сбоя она повторяет очистку, а не создаёт сессии заново. Удаление обычного поддерева сохраняет соседей и независимый иммунитет; удаление зиготы охватывает весь организм. Отсутствующий старый проект или корень при обнаружении агрегата не восстанавливается автоматически. Модель не получает инструмент удаления; архивное восстановление не отменяет явное удаление пользователем.

`SessionHistoryDeletionTest` проверяет поддерево и весь организм, перезапуск после сбоя удаления проекции, обязательное завершение очистки, отказ при UNKNOWN и успешную повторную сверку после восстановления хранилища вопросов. UI отменяет всех известных владельцев до ожидания, сохраняет закреплённые запросы при отказе и показывает причину. `RequestPinViewModelTest` проверяет этот порядок для удаления проекта, всех сессий и одного поддерева. Результаты сфокусированных запусков сохранены в `session-infrastructure-verification/deletion-focused-2026-09-10.json`.

## Предложения иммунитета в интерфейсе

`CodingUi.organisms` получает сохранённые агрегаты из store flow. Ожидающее предложение помечает проект и независимую сессию иммунитета как требующие ответа. `ImmunityInterventions` в этой сессии композирует публичные `PaperPanel`, `PaperButton`, `PaperDialog`, `PaperScrollArea` и `PaperFocusAnchor`: список показывает доказательства, затронутые сессии, разрешённые действия и подтверждённое состояние результата.

`MagicPaperViewModel.approveImmunityIntervention()` вызывает app-only API сервиса с точными `organismId` и `proposalId`. Удаление получает отдельное подтверждение с поколением цели; для корня перечень включает независимый иммунитет. Смена поколения отключает подтверждение. UNKNOWN/ACCEPTED предлагают проверку результата по прежней идентичности, а не повтор эффекта. Завершение запроса не переключает выбранный проект или сессию; post-projection уведомление обновляет существующую UI-проекцию.
