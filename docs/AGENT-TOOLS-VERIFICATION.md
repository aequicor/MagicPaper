Контракт интеграции проверяет принадлежность результатов и авторство, режим, поколение,
неизменяемый запрос и fingerprint, владение рабочей копией и потерю подтверждения внешнего
эффекта. JVM-сценарии используют настоящий Git и внедряемый исполнитель проверок для
контролируемых исходов и отказов. Они сохраняют отдельную копию при конфликте или
неизвестном исходе; наличие SHA само по себе не означает VERIFIED. Сохранённые команды,
exit code и вывод доступны через отдельное чтение, а восстановление выполняет только
очистку и сверку. Вложенный результат сохраняет `integrationId`, общий SHA и проверки,
при этом первоначальные source path/base commit и запись владения не подменяются.
Изменения собственных файлов, другое поколение, ложный SHA или выдуманные проверки
отклоняют привязку; принятый общий результат допускается для интеграции следующим родителем.

Проверки иммунитета охватывают реальное пробуждение по событию без модели, отсутствие
вмешательства по одной жалобе, допустимые обратимые действия, отклонение старого поколения,
пользовательскую остановку иммунитета и отказ от предложения. Пересоздание зиготы оставляет
новое поколение для нового запроса; ребёнок требует правил, источников и подтверждённого
исхода прежних операций. Проверены резерв и интервал повторов, UNKNOWN-интеграция без
квитанции, полный обход квитанций разных запросов/native-buckets, потерянный ответ запуска
без повторного старта, подтверждённое удаление с сохранением аудита и запрет считать
checkpoint остановки доказательством удаления. UI-сценарии проверяют отдельное подтверждение
удаления и чтение неопределённого результата; в отчёте указаны изображения модальных окон.

Первый промежуточный запуск этого набора содержал 73 теста и две ошибки: таймаут нового
event-теста из-за смешения виртуального тестового времени с реальным dispatcher и фикстуру
вспомогательного планировщика. После исправлений и добавления связанных сценариев приведённый
выше адресный запуск прошёл полностью. Эти результаты не включают Windows UI и не заменяют
полную проверку остальных модулей; успешность итогового полного запуска здесь не заявляется.

## Сценарии

`AgentToolsTest` проверяет каталог ролей и режимов, отсутствие возможностей без плана,
ошибочные аргументы, неизвестные инструменты, доверенный контекст и владельца статистики,
параллельные вызовы, повторную доставку, отмену и блокировку неоднозначного повтора.
Опросник ожидает подтверждённый ответ и не выдаёт разрешения. Наблюдатели скрывают секреты,
а нативные события не запускают команды повторно.

`OrchestrationToolsTest` проходит весь путь: предложение через `plan.propose` →
подтверждение → рабочие сессии → `stage.handoff` → `stage.resolve` → приёмка.
Проверяются чужие идентификаторы, устаревшая ревизия, ограничения автоматических сообщений,
выборочная пауза зависимых этапов, расписание, фиксированное время ожидания и восстановление
доставки при потере окончательной квитанции. Старые сохранённые решения проходят через
команды; текст исторического сообщения не становится действием.

Карточка родительской команды остаётся видимой при вложенном планировании. Ключи вызовов
сохраняются при переходе в историю; сохранённые дочерние вызовы не дублируются в живом
ответе. Проверены состояния ожидания/отмены, раскрытие и большой вывод. Render-тест сохраняет
изображение в `shared/build/reports/agent-tools/cancelled-tool.png`.

`CodexToolEventsTest` проверяет произвольные MCP-вызовы, прогресс, результат, ошибку,
отмену и разделение потоков. `AgentToolBridgeTest` проверяет единый объект разрешённых
MCP-серверов в защищённом режиме: пустой корневой список не перекрывает мост приложения.
В обычном режиме сохраняются унаследованные настройки серверов пользователя.
